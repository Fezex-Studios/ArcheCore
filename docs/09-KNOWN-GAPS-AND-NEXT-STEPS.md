# Known Gaps & Next Steps

These are real inconsistencies found while reading the current code — not
hypothetical concerns. Fix the first two before building much more on top
of `worldserver.db` or the client dispatcher; the rest are lower-urgency
but worth knowing about.

## 1. Two schema-management systems fighting over `worldserver.db`

**The problem** (full detail in
[03-DATABASE-AND-PERSISTENCE.md](03-DATABASE-AND-PERSISTENCE.md)): EF Core
migrations (`Migrations/*.cs`, driven by `WorldDataDbContext`) and a raw
SQL patch runner (`GameDataPatchRunner`, `SQL/patches/*.sql`) both target
the exact same file, and `Database.Migrate()` is never called anywhere in
the codebase — meaning the migrations exist as C# but the patch runner is
the only thing that actually mutates the database on a normal boot. Worse,
migration `AddNpcInteractRange` and patches `005`/`006` create the *same
two tables* with incompatible schemas (the migration's `NpcTemplates` has
an `InteractRange` column; the patch's doesn't).

**Decision: EF Core migrations.** Better long-term ergonomics (real
up/down migrations, LINQ queries, compile-time-checked `DbSet<T>` access)
and — importantly for a team that includes non-programmers — it lets
content (NPC placement, stats, prices) live in plain JSON files that a
designer edits directly, completely separate from schema. The patch
runner's raw `.sql` files were never a workflow anyone but a programmer
could safely touch.

One clarifying finding before the fix: patch `007_npc_template_data.sql`
inserts into an `InteractRange` column that patch `005`'s own
`CREATE TABLE IF NOT EXISTS` doesn't define. Since the patch runner throws
and aborts boot on any failing statement, and the server has clearly been
booting fine with `InteractRange` populated, patch 005 has almost
certainly been a no-op on every dev machine so far — the table already
existed in the EF-migration shape (`AddNpcInteractRange`) before the
patches ever ran, meaning `dotnet ef database update` was run by hand at
some point. The patches have been quietly seeding data on top of an
EF-created schema the whole time, not competing with it in practice, which
makes formalizing EF as the one true schema system a much smaller jump
than it first looked.

**Concrete fix, fully spelled out in `code/MIGRATION-STEPS.md`:**

1. `WorldServer.StartAsync` calls `WorldDataDbContext.Database.MigrateAsync()`
   instead of `GameDataPatchRunner.RunAsync()`.
2. The three pure-schema patches (`005`, `006` — fully superseded by
   `AddNpcInteractRange`) are deleted outright.
3. The three seed-data patches (`007`, `010`, `023` — all auto-generated by
   the Unity "NPC Spawner Exporter" / "ArcheCore Dev Tools") insert *data*,
   not schema — they're not something EF migrations replace. Before
   deleting them, make sure whatever seeding tooling you're using can
   already reproduce the rows they used to insert.
4. `GameDataPatchRunner.cs` and `SQL/patches/` are deleted once the above
   is verified.

**Do this before adding shop/inventory tables to `worldserver.db`** — new
tables should be EF migrations from day one. How rows get into them is a
separate decision, kept intentionally out of scope here — don't revive
the SQL-patch habit for it, but there's no requirement to use any
particular seeding mechanism either.

## 2. Client packet dispatch is manual, server-side is automatic

**The problem** (full detail in
[08-CLIENT-ARCHITECTURE.md](08-CLIENT-ARCHITECTURE.md#the-dispatch-gotcha)):
`ClientPacketDispatcher.AutoRegister` exists, works, and is even documented
as the intended pattern in `ADDING_PACKETSv2.md`'s quick reference — but
`ClientNetwork.RegisterHandlers()` still hand-registers every W2C opcode,
and none of the `W2CHandlers` classes carry `[PacketOpcode]`. This is
exactly the "handler exists but nobody wired it in" bug class the
attribute system was built to eliminate on the server side, and it's still
live on the client.

**Recommended fix**, in order:

1. Add `[PacketOpcode(Opcodes.X)]` to every existing class in
   `Assets/ArcheCore.Client/Networking/W2CHandlers/`, matching the opcode
   it's already manually registered against in `RegisterHandlers()`.
2. Replace the body of `RegisterHandlers()` with a single call:
   ```csharp
   dispatcher.AutoRegister(typeof(ClientNetwork).Assembly);
   ```
3. Delete the now-redundant manual `Register(...)` calls.

`ClientPacketDispatcher.AutoRegister` already handles the parameterless-
constructor case every existing client handler needs (see the doc comment
on that method) — no further changes to the dispatcher itself required.

## 3. The stale `Shared/Opcodes.ts`

`ArcheCore_Server_Persistence/src/Shared/Opcodes.ts` duplicates the
`ProtocolPersistence` enum name from the canonical
`protocol.persistence.ts`, already drifted (it's missing `HelloWorld`,
`CharacterCreate`, `CharacterList`, and the two matching response values,
and has a `P2WErrorResponse = 6` that doesn't exist in the real one — see
[02-NETWORKING-AND-PACKETS.md](02-NETWORKING-AND-PACKETS.md)). Confirm
nothing imports it, then delete it — it's a landmine for exactly the kind
of accidental-import mistake `ADDING_PACKETSv2.md` warns about in its
worked examples.

## 4. `SendLootMessage` is a UI-only placeholder, not a real item grant

`LuaPlayer.SendLootMessage(itemName)` sends `W2CInteractLootPacket`, which
the client turns into a toast/message — it does not touch any inventory,
because there isn't one yet. Every `npc_guard_example.lua`-style script
that calls it today is cosmetic. If a shop system is next, inventory comes
first (or alongside it) — see
[07-BUILDING-A-FEATURE-END-TO-END.md](07-BUILDING-A-FEATURE-END-TO-END.md)
for a concrete `inventory` table + purchase-flow sketch that would also
retire this placeholder by giving `SendLootMessage`'s callers a real grant
path to call instead.

## 5. `LuaPlayer.Kick(reason)` never sends `reason` anywhere

```csharp
public void Kick(string reason)
{
    peer.Disconnect();   // `reason` is unused
}
```

If any admin/moderation script relies on the player seeing why they were
kicked, it currently won't happen — `Disconnect()` uses LiteNetLib's
default disconnect data. Fix is small: send a one-off packet (or attach
`reason` as LiteNetLib disconnect data via the `Disconnect(byte[] data)`
overload) immediately before calling `Disconnect()`.

## 6. Unfired `PlayerEvent` values

`OnDisconnect`, `OnLevelUp`, `OnChat`, and `OnDeath` are reserved enum
values with no corresponding `_luaEngine.FireEvent(...)` call anywhere in
the C# code yet — only `OnConnect` and `OnInteract` are live (see
[04-LUA-SCRIPTING.md](04-LUA-SCRIPTING.md)). Not a bug, just a reminder
that a script calling `Server:RegisterPlayerEvent(4, ...)` (`OnChat`) today
will register successfully and then silently never fire. Worth firing
`OnChat` from `C2WChatHandler` fairly early since it's the cheapest one to
wire up and immediately useful (profanity filtering, chat commands,
moderation hooks all become possible from Lua once it fires).

## 7. Name validation for character creation exists in exactly one place

`C2WCreateCharacterHandler` checks `2 <= name.Length <= 20` server-side;
`W2PCharacterCreateHandler.ts` does no re-validation before inserting.
Fine today since the WorldServer is the only thing that ever calls the
persistence create endpoint, but if you ever add a second caller of that
Node handler (an admin tool, a migration script), it would bypass this
check entirely. Consider duplicating the length check (or a stricter one,
e.g. banning empty/whitespace-only names after trim, which the current
check already prevents, or filtering disallowed characters) inside
`W2PCharacterCreateHandler.ts` itself.

## Suggested order of operations

If you're picking this project back up to build the shop system (or
anything else) on top of what's here:

1. Fix #1 (schema management) first — you don't want new inventory/shop
   tables joining a database with two competing owners.
2. Fix #2 (client auto-registration) next — every new feature from here
   on adds at least one new W2C packet, so this pays for itself
   immediately and removes a whole class of "why isn't the UI updating"
   bugs.
3. Delete #3 (stale `Opcodes.ts`) — five minutes, zero risk.
4. Build the shop/inventory system per
   [07-BUILDING-A-FEATURE-END-TO-END.md](07-BUILDING-A-FEATURE-END-TO-END.md),
   which naturally retires #4 (`SendLootMessage` placeholder) as part of
   giving items a real home.
5. Wire up `OnChat` (#6) while you're touching chat-adjacent code anyway,
   since a shop UI will likely want chat-adjacent moderation/logging too.
6. #5 and #7 are small, low-risk fixes — good candidates for whenever
   you're already touching `LuaPlayer` or `W2PCharacterCreateHandler.ts`
   for something else.
